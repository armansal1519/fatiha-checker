# بهینه‌سازی سرعت قرائت زنده

تاریخ: ۲۰۲۶-۰۹-۱۸. دستگاه: Intel Core i7-13700H، Windows، PyTorch 2.11.0+cpu، شش thread، float32. مدل و revision قبلی حفظ شده‌اند. کارت‌های گزارش‌شدهٔ دستگاه Intel Iris Xe و Arc A370M هستند؛ اجرای برنامه در این تغییر همچنان CPU است و runtime یا درایور GPU نصب نشد.

صوت‌های مجموعه و گزارش‌های خام JSON این ارزیابی محلی‌اند و همراه مخزن Git توزیع نمی‌شوند. این گزارش مبنای تاریخی HTTP است؛ نتیجهٔ نسخهٔ WebSocket در [گزارش دموی فعلی](WEBSOCKET_DEMO_REPORT.md) آمده است.

## علت تأخیر و تغییرها

- نسخهٔ قبل هر ۲ ثانیه تا ۱۰ ثانیه صوت می‌فرستاد و برای رنگ‌زدن کلمه معمولاً دو مشاهده لازم داشت. بنابراین تأخیر دیده‌شده مجموع جمع‌آوری صدا، اجرای مدل و انتظار برای مشاهدهٔ دوم بود.
- برنامهٔ جدید هنگام خواندن تقریباً هر ۰٫۸ ثانیه یک پنجرهٔ حداکثر ۶ثانیه‌ای می‌فرستد. یک درخواست در حال اجرا مجاز است؛ پس از پاسخ، تازه‌ترین صدا انتخاب می‌شود. فشار پردازشی روی دستگاه ضعیف می‌تواند فاصلهٔ واقعی را بیشتر کند.
- در مکث/پایان یا گم‌شدن موقعیت، زمینهٔ ۱۰ثانیه‌ای حفظ شده است. سکوت پس از آخرین صوت تا حاشیهٔ ۲۵۰ میلی‌ثانیه محدود می‌شود. قاعدهٔ دو مشاهده برای رنگ‌های حین خواندن حفظ شده؛ مکث همچنان کلمات کامل را مستقیم بررسی می‌کند.
- در مسیر زنده، آماده‌سازی مرجع و هم‌ترازی صفات پیشرفتهٔ تجوید حذف شده‌اند. همان feature extractor، مدل و decoder رسمی آوایی استفاده می‌شوند. وزن، float32، تنظیم شش thread و قواعد تشخیص اختلاف تغییر نکرده‌اند. API دقیق آیه بدون تغییر است.
- `torch.inference_mode` فعال است. برای صدای کاملاً یکسان فقط آخرین digest و متن پیش‌بینی نگهداری می‌شود تا بررسی پایانی بتواند بدون اجرای دوبارهٔ شبکه، قواعد وقف و کامل‌بودن کلمه را اعمال کند. صوت سرور ذخیره نمی‌شود.

## پروفایل CPU

در `profile_live.py` یک فایل واقعی صرفاً برای اندازه‌گیری بار پردازش تکرار شده است؛ این صوت بلندشده، شاهدی برای دقت نیست. بعد از اجرای گرم‌کننده، میانهٔ دو اجرا ثبت شد:

| طول صوت | forward با ۶ thread | کل مسیر آوایی و تطبیق |
|---|---:|---:|
| ۲ ثانیه | ۰٫۳۸۲ ثانیه | ۰٫۳۸۸ ثانیه |
| ۶ ثانیه | ۰٫۹۶۵ ثانیه | ۰٫۹۸۴ ثانیه |
| ۱۰ ثانیه | ۱٫۸۱۴ ثانیه | ۱٫۸۴۱ ثانیه |

هم‌ترازی متن فقط حدود ۲ تا ۷ میلی‌ثانیه طول کشید. شبکه گلوگاه اصلی بود. دو و چهار thread در پنجره‌های بلند این دستگاه کندتر از شش thread بودند و انتخاب قبلی حفظ شد. جزئیات: `live-profile-before.json`.

## مقایسهٔ قبل و بعد با مدل واقعی

`benchmark_live_latency.py` درخواست واقعی HTTP به localhost می‌فرستد. ساعت جمع‌آوری صوت و قاعدهٔ نمایش دو مشاهده شبیه‌سازی می‌شوند؛ زمان HTTP واقعی است و وارد زمان‌بندی درخواست بعدی می‌شود. در این سناریوها مکث بین‌خواندن لحاظ نشده؛ بررسی پایانی زمینهٔ ده‌ثانیه‌ای دارد. پس این اعداد، زمان مشاهدهٔ خطا پس از تلفظ یک حرف مشخص یا تأخیر مستقیم میکروفن نیستند.

| ضبط از آرشیو L2-KSU | نخستین رنگ قبل | نخستین رنگ بعد | وضعیت نهایی کلمات |
|---|---:|---:|---|
| Sp8_NF_S1_3 | ۴٫۷۷ ثانیه | ۲٫۹۳ ثانیه | یکسان |
| Sp3_NM_S2_5 | ۳٫۵۲ ثانیه | ۲٫۹۵ ثانیه | یکسان؛ چهار کلمه سبز |
| Sp1_M_S2_2 | رنگی ظاهر نشد | رنگی ظاهر نشد | تطبیق ناکافی در هر دو |
| Sp15_M_S2_3 | ۴٫۷۶ ثانیه | ۳٫۹۳ ثانیه | یکسان؛ سه کلمه با اختلاف |
| Sp11_NM_S1_5 | ۴٫۷۲ ثانیه | ۲٫۹۸ ثانیه | یکسان |
| Sp11_F_S1_1 | ۴٫۷۲ ثانیه | ۳٫۹۱ ثانیه | یکسان |

میانهٔ نخستین رنگ در پنج فایل قابل‌تطبیق از ۴٫۷۱۶ به ۲٫۹۸۳ ثانیه کاهش یافت، حدود ۳۷٪ زودتر. میانهٔ زمان پاسخ درخواست‌ها از ۰٫۷۵۱ به ۰٫۵۹۷ ثانیه رسید. تعداد درخواست‌ها در این اجرا از ۲۱ به ۴۲ افزایش یافت؛ پایین‌ترآمدن تأخیر، به معنی کاهش کل مصرف CPU نیست. درخواست‌های جدید و قدیم طول یکسان ندارند؛ زمان پاسخ جدول، سرعت ذاتی یکسانِ شبکه را مقایسه نمی‌کند. خروجی‌های کامل در `live-latency-before.json` و `live-latency-after.json` ثبت‌اند.

در آزمون جداگانهٔ `verify_live_fastpath.py`، هر دو مسیر روی **همان ۲۰ پنجرهٔ صوتی** اجرا شدند. متن آوایی تمام موارد دقیقاً یکسان بود؛ میانهٔ نسبت زمان مسیر زنده به کامل حدود ۰٫۹۰ بود. استفادهٔ دوباره از پیش‌بینی صدای یکسان میانهٔ ۰٫۰۰۰۱۷ ثانیه طول کشید. جزئیات در `live-fastpath-verification.json` است.

## اعتبارسنجی و محدودیت

۵۷ آزمون Python و ۶ آزمون JavaScript موفق‌اند، شامل سقف حافظه، انتخاب پنجره بدون حذف زمینهٔ بازبینی، حاشیهٔ سکوت، زمان‌بندی مکث، درخواست کند بدون صف، کلید cache، آماده‌نبودن مدل و آزادشدن قفل در شکست اجرای مدل. رابط مرورگر با نمونهٔ واقعی صحیح و دارای خطای معلوم بررسی شد؛ خروجی مدل ساختگی نیست. ضبط واقعی میکروفن نیز در یک نوبت ۱۴ثانیه‌ای درخواست‌های موفق به مسیر جدید فرستاد و بررسی پایانی به وضعیت آماده برگشت؛ این صوت برچسب تلاوت نداشت. خطای JavaScript در مرورگر مشاهده نشد.

یکسان‌بودن خروجی در این نمونه‌ها تضمین دقت روی صدای همهٔ کاربران نیست. پنجرهٔ کوتاه‌تر می‌تواند در خواندن آهسته، نویز یا کشش بلند زمینهٔ کمتری داشته باشد. بازگشت به پنجرهٔ بلند و بازبینی پایانی کمک می‌کنند، ولی رنگ زنده موقت می‌ماند. خطاهای قدیمی مدل و هشدارهای اضافی آن با این تغییر سرعت برطرف نشده‌اند.

## مسیر بهبود بعدی

برای محصولی با واکنش خیلی سریع، محل خواندن و قضاوت تلفظ باید دو مرحله باشند: مکان‌نما سریع به‌روز شود و خطای حروف/حرکات با زمینهٔ کافی تثبیت شود. برای کاهش بنیادی هزینهٔ اجرای شبکه، GPU سازگار یا یک مدل کوچک‌تر با پردازش جریانی و حافظهٔ بخش قبلی باید جداگانه ارزیابی شود. کم‌دقت‌کردن عددی مدل (مثلاً INT8) نیز فقط پس از سنجش سرعت روی سخت‌افزار واقعی و آزمون حروف/حرکات قابل قبول است؛ در این نسخه اعمال نشده است.

مدل کنونی در مستندات رسمی حدود ۶۶۰ میلیون پارامتر دارد و نمونهٔ رسمی، CPU/CUDA را نشان می‌دهد: [Quran Muaalem](https://github.com/obadx/quran-muaalem). راهنمای عمومی بهینه‌سازی inference: [PyTorch performance tuning](https://docs.pytorch.org/tutorials/recipes/recipes/tuning_guide.html).

## بازاجرا

```powershell
.\.venv\Scripts\python.exe -m pytest -q
node --test tests/test_live_audio.mjs tests/test_live_cadence.mjs
.\.venv\Scripts\python.exe -X utf8 verify_live_fastpath.py
# نیاز به سرور روشن؛ قبل از مقایسه، نسخهٔ متناظر سرور باید فعال باشد.
.\.venv\Scripts\python.exe -X utf8 benchmark_live_latency.py --label rerun --cadence 0.8 --window 6
```

Node فقط ابزار آزمون توسعه است. اجرای برنامه همچنان صرفاً `python app.py` است.
